## Concrete activation blockers and drift beyond the older review

1. **Shared codec does not exist yet.** `broker_wire.rs:19-26` imports private `session_wire::Frame`, nonexistent `MessageAssembler`, and nonexistent `read_frame_bytes`; `broker_writer.rs` relies on private `Sending` plus missing `from_payload`, `next_frame`, and `mark_sent`. Active `session_wire.rs::MessageReader` still combines reading, framing, assembly, duplicate detection, and limits (`178-385`). `Payload` lacks `into_parts`/`from_parts`. Extract from the current codec; do not create a second serializer/assembler or deserialize via `Value` and thereby lose duplicate-field rejection.
2. **Staged spawn regresses startup ownership.** `broker_connection.rs::connect_with_broker` (`55-119`) spawns and awaits handshake directly in the public future, with `ChildGuard` dropped on failure/cancellation. Active `session_supervisor.rs::connect_with_options/connect_owned` (`79-181`) retains a separate startup owner, latches caller abandonment, and explicitly kills/waits before returning errors or declares reaping unconfirmed. Broker activation must reuse/port that ownership before exposure, including failed handshakes and abandoned startup. `ChildGuard::Drop` (`process.rs:127-146`) is fallback cleanup, not an observed reap acknowledgement.
3. **Later host contracts are absent in the staged branch.** Broker startup hardcodes package cwd (`broker_connection.rs:65`) and has no `ComponentSessionOptions` or `SessionPayloadLimits`; its `SessionInner` construction (`159-171`) omits active `limits`. Current `MessageReader` validates declared incoming request/reply sizes before spool admission (`session_wire.rs:200-235`), `Sending::new` now receives limits (`399+`), and server reply limits are fixed at admission (`session_server.rs:86-94`). `BrokerMessageReader` (`149-168`) has no corresponding local-limit plumbing. Preserve unlimited defaults, explicit configured caps, trusted control-lane distinction, and immutable cwd selection in the shared extraction.
4. **Typed failure and pending-reply drift makes old patches unsafe to apply verbatim.** Active `session.rs:29-31` uses `SessionFailure`; `broker_connection.rs:151-157` and `broker_completion.rs::complete` (`39-92`) still supply `String` failures. The session patch's context still says `Result<Payload,String>` and modifies old `DeferredControl::release`; current code has `release_reply` and public `PendingComponentReply`/`start_with_cleanup`. Rebase scoped admission and reentry checks onto every current entrypoint; preserve structured local size-limit errors, accepted ownership, detached cleanup lanes/send fences, and exact first causes.
5. **No component-side broker connection lifecycle is implemented.** `ComponentServer` has no negotiated dependency client, scope attachment/access, or broker demultiplexing, and no supervisor feeding `DependencyClient::complete/fail`. Implement an owned single reader/writer path that fails dependency waiters on EOF/parser/writer/task failure, preserves plain `stdio`, and drains accepted reverse work during normal close.
6. **Component reverse-response parse is still waiter-owned.** `DependencyClient::complete` (`broker_client.rs:308-325`) removes pending capacity/cancellation ownership on wire completion; `call` (`299-305`) subsequently invokes `Payload::into_value`, whose `spawn_blocking` parser (`session_wire.rs:83-88`) can outlive an abandoned waiter without an acknowledged join. Supply a retained component-side decode owner/cancellation receipt before calling this finished. Do not apply the 8 MiB reverse-*request* cap to responses or native histories.
7. **Linking/build metadata and process proof remain gates.** The runtime patch adds UUID v4, but current `component-host/Cargo.toml` does not declare it. Update Cargo/Bazel dependency metadata in the coordinated implementation. The documented previous formatting/disposable patch-application checks are not current compilation or bidirectional runtime evidence; the patches now target stale method/types as above.

## Ownership already represented in staged code (preserve, do not count as active proof)

- `HostDependencyRegistry::{register,register_optional}` owns allowed descriptor/implementation/live authority per connection (`broker_host.rs:47-104`), bounded to 32 grants. `BrokerHost::scope` keeps host-only `HostOperationScope.request_context` after parent waiter loss (`273-323`; `broker_api.rs:176-199`). `validate` checks grant, service/version/method, parent/context generations, and current authority (`401-451`); `run` checks around the async leaf service (`454-476`). Opaque identity/request context are redacted rather than copied into plugin config.
- `BrokerDispatcher::dispatch` owns handler and monitor, reserves response capacity, joins handler destruction, then waits for final physical-flush acknowledgement before removing the active record (`broker_dispatch.rs:64-163`). `finish_parent` revokes under the same admission lock (`178-190`). `ParentCompletions::complete` retains the parent response/capacity until those joins (`broker_completion.rs:37-100`). These are meaningful intended ownership boundaries to retain through refactoring.
- `broker_decode::decode/decode_reader` owns the reverse-request spool/parser, enforces 8 MiB only after spool completion, and joins controlled cancellation (`broker_decode.rs:20-126`). `broker_spool`/writer similarly intend joined serialization. Neither count limit nor request parse cap currently bounds all temporary spool bytes. Existing ordinary `Payload::{from_value,into_value}` still use direct blocking tasks; async reader/writer join alone cannot prove they joined.
- Separate ordinary/broker ID maps and separate completion/cancellation/response lanes are necessary namespaces/capacities, not accidental duplication to collapse. Broker service grants must remain separate from package dependency resolution and user JSON configuration. Process construction/startup policy, physical codec validation, and terminal cleanup mechanics are the duplication to unify or reuse.
- Declaration-versus-grant gap: current host registry sets required/optional status; worker `DependencyClient::negotiate` receives explicit descriptors. No manifest declaration drives either. Decide a bounded versioned service-requirement declaration during SDK activation and keep actual grant composition host-owned. There is no justification for generic HTTP/credential capability from metadata alone.
- Negotiation detail to document deliberately: staged `BrokerHost::acknowledge` (`243-252`) requires exact operation-set equality for a granted descriptor, whereas the proposal describes supported subsets. Choose and test the intended compatibility rule; do not silently broaden it when wiring manifests. Task-local leaf reentry checks cannot infer arbitrary spawned-helper ancestry; retain the explicit leaf restriction until a real acyclic dependency model exists.

## Guard scope and hardcoded package capability constraints

- The initial rule is **all persistent callbacks from a leaf handler**, not merely recursion into its original process. `BrokerHost::run` enters `IN_DEPENDENCY_HANDLER` (`broker_host.rs:464`); the session patch checks the common old `start`, `DeferredControl::release`, `ComponentSession::close`, and `ComponentBinding::connect`. Staged `connect_with_broker` checks before spawning. Therefore a thread-storage broker service calling selected persistent file-search also violates this first leaf contract. Defer that consumer to explicit bounded acyclic dependency-graph support; spare queue capacity does not make it legal. Nonblocking preauthorized cleanup Drop remains available; one-shot auth is deliberately separate.
- Porting the guard only where the old patch puts it is insufficient: current callers can enter `connect_with_limits` or `connect_with_options` directly, and `DeferredControl::release_reply` exists. Guard the current centralized pre-spawn/admission/waiting paths before ownership leaves the task-local context, and test held session clones as well as constructors. Spawned helper tasks do not automatically inherit the task-local marker; the explicit implementation restriction remains necessary until a propagated ancestry contract exists.
- `ComponentCatalog::read_manifest` hardcodes supported kinds (`catalog.rs:249-266`): tool, context, lifecycle, model_transport, presentation, auth, thread_store, attachment_store, file_search. **model_catalog is currently rejected.** It separately hardcodes thread_store version 2, file_search version 1, and all other kinds version 1 (`267-275`). Native catalog installation therefore also needs the narrow versioned kind/contract admission change plus package tests. The existing generic metadata `Value` does not establish a service requirement, negotiation, or permission. A general extensible component-kind registry is a separate platform endpoint gap, not justification to weaken current kind validation in this first slice.
