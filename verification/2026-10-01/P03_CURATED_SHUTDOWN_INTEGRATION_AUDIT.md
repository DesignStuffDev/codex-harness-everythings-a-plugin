Read-only audit of native source `cb9f7409071e64293801e52b21a2fc1d1a87de6f` / tree `9c07e9c6e1a66be41cd675c290d4c593d336cbbc`; root reports development checkpoint `8d1216a3` published. No tests or repository mutations were performed; source hashes are in [the source audit manifest](p03-curated-shutdown-audit-sources.json).

The next integration needs **a process-final owner, exact worker completion, and ownership of callbacks**. Calling the existing stop request from every `PluginsManager::drop` or embedded processor shutdown is unsafe: the gate is process-global and Closing is permanent, while the TUI intentionally shuts down and restarts an embedded server on provider change ([lib.rs:1858](https://github.com/DesignStuffDev/codex-harness-everythings-a-plugin/blob/cb9f7409071e64293801e52b21a2fc1d1a87de6f/codex-rs/tui/src/lib.rs#L1858)). Two embedded servers can also exist in one process. Per-runtime teardown must close that runtime's callback/config admission; only an explicit process-final owner may permanently close the shared native gate.

## Publication ordering before a durability claim

Current [publish_curated_repo:625](https://github.com/DesignStuffDev/codex-harness-everythings-a-plugin/blob/cb9f7409071e64293801e52b21a2fc1d1a87de6f/codex-rs/core-plugins/src/startup_sync.rs#L625) admits activation+SHA as a pair. Activation renames old repo into a retained TempDir backup, then staged repo into place; [SHA writing:714](https://github.com/DesignStuffDev/codex-harness-everythings-a-plugin/blob/cb9f7409071e64293801e52b21a2fc1d1a87de6f/codex-rs/core-plugins/src/startup_sync.rs#L714) is plain `fs::write`. There is no journal, atomic SHA replacement or fsync protocol. A crash between renames/SHA can leave mismatched state. [Cache refresh:375](https://github.com/DesignStuffDev/codex-harness-everythings-a-plugin/blob/cb9f7409071e64293801e52b21a2fc1d1a87de6f/codex-rs/core-plugins/src/loader.rs#L375) subsequently installs/uninstalls plugin cache versions and is another mutation boundary.

Recommended recoverable unit: under the existing stable lock, durably record generation, old/new revision and validated stage/backup paths; persist the stage; record intent before each irreversible rename; atomically replace and sync the SHA; record committed before publishing cache/consumer notifications; only then retire backup/journal and release ownership. Recovery runs before stale-directory GC or new sync and chooses a validated old pair or completed new pair. Never delete journal-referenced directories. Cache mutations need their own completed/uncertain disposition and version-bound inputs. A lock acquired after host death does not prove escaped helpers are fenced; unknown custody still needs an external termination/fencing prerequisite before recovery.
