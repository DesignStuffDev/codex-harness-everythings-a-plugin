# Session ownership prerequisite for selected context replay

Design only, 2026-09-30. Production source is frozen for the full workspace/storage checkpoint. This document does not activate [`component_replay.rs`](../codex-rs/core/src/session/component_replay.rs), add tests, or claim context runtime completion. It refines the prerequisite in [`CONTEXT_REPLAY_ACTIVATION.md`](../codex-rs/core/src/session/CONTEXT_REPLAY_ACTIVATION.md).

## Current behavior and concrete failure window

[`Session::new`](../codex-rs/core/src/session/session.rs) acquires persistence, constructs native services, calls extension thread-start contributors, creates `Arc<Session>`, emits `SessionConfigured`, installs MCP, starts MCP/environment followers and prewarm, then reconstructs initial history. Required MCP installation and referenced-fork materialization can already fail after the Session exists. Selected replay would add another error/cancellation boundary at history reconstruction.

The constructor's error arm calls only `LiveThreadInitGuard::discard`. Its ordinary caller supplies no [`SessionStartup`](../codex-rs/core/src/session/startup.rs). Consequently a failure after construction does not invoke the session's existing service teardown. Merely dropping the local Session Arc is insufficient when a startup task or another observer retains it. Cancellation can also drop the constructor before its explicit error arm runs.

Managed isolated starts have a stronger wrapper in [`start_thread_until`](../codex-rs/core/src/thread_manager/managed.rs): it retains persistence acquisition, constructed Session and eventually SessionIo, drops initialization before cleanup, and then runs either normal loop shutdown or direct service teardown. That holder is optional, its `cleanup` is not independently supervised, and ordinary selected sessions do not use it. Reusing its resources is appropriate; treating it as an already universal lifetime solution is not.

[`shutdown_session_runtime`](../codex-rs/core/src/session/handlers.rs) sets `SessionState.shutting_down`, takes/joins websocket and shell prewarm, shuts realtime down, aborts active turns, drains hooks, terminates unified exec, shuts code mode and MCP down, drains code-mode messages, and invokes SessionEnd/thread-stop callbacks. Repeating the function repeats callbacks. A boolean early-return would also be wrong: a second waiter could report completion while the first teardown is still running, or after that waiter was cancelled.

[`SessionLoopTermination`](../codex-rs/core/src/session/mod.rs) currently shares a lazy future that awaits the loop JoinHandle and ignores its JoinError. Normal loop EOF runs cleanup, but a cancelled/panicked loop does not reach that epilogue. A replay owner held only inside the loop would revoke on drop without making the existing completion future wait for native/replay cleanup.

## Minimal ownership spine

Use one startup resource holder for ordinary and managed construction, one nonclone terminal owner, and one independently driven teardown completion. Do not put an owning Session Arc or submission sender in the completion state stored on Session.

1. **Mandatory startup ownership.** Resolve the optional managed `SessionStartup` to a per-attempt holder for every constructor. Use its single `LiveThreadInitGuard` for acquisition in both paths; remove the separate local-versus-managed guard ownership branches. A nonclone `SessionLaunchGuard` owns this holder from before acquisition. Dropping a constructor or its error cleanup must schedule the same supervised cleanup, not separately race native teardown against `LiveThreadInitGuard::drop`'s persistence discard.
2. **Publish without an await gap.** Immediately after creating `Arc<Session>`, register it in the launch guard before the first subsequent await. Attach the selected `ReplayOwner` to that guard synchronously before awaiting replay readiness. Early Session observers receive service access, not terminal ownership. The holder's Session lookup should be weak (or explicitly taken on transfer/close); retaining the startup holder must not keep a closed Session alive indefinitely.
3. **Return ownership through the entire handoff.** Return a named `InitializedSession { session, launch }` from `Session::new`; the launch guard remains armed through service-tier warnings and all awaits in `spawn_internal`. It owns persistence in the uncommitted state until submission-loop ownership is accepted. Tests that call the constructor directly must explicitly take or close the owner. Returning a bare Session Arc and dropping the guard is not valid.
4. **Transfer into an independent loop supervisor.** In one non-awaiting handoff, switch persistence disposition to normal running ownership, move the terminal owner into a supervisor, spawn the submission loop, and publish SessionIo. The supervisor owns the loop JoinHandle and runs whether anyone polls termination. It awaits the loop, ensures runtime teardown and persistence settlement, observes replay cleanup, drops its Session Arc, and only then publishes retained completion. `SessionLoopTermination` can retain its existing unit-returning API as a watch-based compatibility facade; a private structured outcome must retain failures instead of silently turning a JoinError into success.
5. **Keep submission senders out of the supervisor.** It must own neither `SessionIo` nor `SessionStartup` containing a strong SessionIo. Otherwise its sender prevents EOF, and waiting for the loop creates a lifetime cycle. The managed wrapper may retain its own SessionIo because it is the explicit lifetime owner, but the transferred terminal payload contains only the Session, replay owner, cleanup state, and persistence disposition. Clear or release ordinary startup-holder ownership after the transfer. Do not await the loop from inside the runtime cleanup worker.

Suggested new private module: `core/src/session/runtime_lifecycle.rs`. Keep acquisition bookkeeping in `startup.rs`; do not add another public harness API. State transitions are:

```text
acquiring -> constructed -> loop_owned -> closing -> closed(outcome)
     \             \            /
      +---------------> closing
```

Before loop ownership, cleanup closes runtime/replay first, then discards the acquired writer (including finishing an in-flight acquisition). After loop ownership, cleanup uses normal writer shutdown; it must never discard a successfully running thread. Record this disposition under the ownership gate, rather than inferring it from whether a Session Arc exists. The existing `Session::new` success-side `live_thread_init.commit()` moves to the handoff. A failed duplicate start must never act on the existing thread's writer.

The existing managed `SessionStartup::cleanup` becomes an adapter: if the loop is owned, request interrupt/shutdown through its IO and await the common completion; if construction has not transferred, join the guarded startup cleanup. Its TaskTracker must cover that completion before registry removal. Preserve the exact Session identity check when removing a managed thread. Multiple managed/error/loop cleanup requests must join one operation.

## One teardown, multiple waiters

`SessionRuntimeCleanup` should hold a synchronous start/admission gate and a retained `watch` result. Starting cleanup atomically chooses the single worker and closes admission; it does not merely install an unpolled async future in an `OnceCell`. The worker owns a temporary `Arc<Session>` and releases it at completion. Shared completion stores only status/report data. Capture the owning runtime handle while constructing services; Drop must not depend on finding a new current runtime. Abrupt destruction of that runtime still cannot promise joined cleanup.

Split the current function into an idempotent entrypoint and a private, once-only body. Preserve the native ordering of realtime/turn abort, hooks, unified exec, code mode, MCP, retained messages and SessionEnd/thread-stop. All callers (`Op::Shutdown`, submission EOF, suspension, constructor failure, loop panic/cancellation and managed cleanup) use the entrypoint.

- At close initiation, revoke replay admission synchronously, then under `SessionState` set `shutting_down`, take pending prewarm and repeat replay revocation. The state-to-replay-gate lock order remains the staged contract. No replay reply or delayed estimated-prefill update may commit afterward. Revocation itself may take only the replay gate and must never acquire SessionState in reverse order.
- Begin replay close immediately, then join native cleanup and replay completion before acknowledging startup cleanup/loop termination. A retained `Arc<SessionReplay>` must remain closed. The nonclone owner survives until this acknowledgement; it is not hidden inside a service Arc.
- A cancelled waiter leaves the worker running. Later callers observe the same report. A teardown panic must produce a retained failure; stages that can call external hooks/contributors need panic supervision so later mandatory cleanup still executes. Mark a callback stage entered before invoking it; do not retry a partially executed callback after panic and claim exactly-once effects. Report the incomplete stage.
- Keep presentation and metrics outside generic cleanup. `Op::Shutdown` retains its turn-count metric, persistence-error event, `ShutdownComplete` and rollout-trace completion. Startup failure and panic cleanup must not synthesize successful shutdown events or duplicate metrics. Existing [`suspend_turn_and_shutdown`](../codex-rs/core/src/session/turn_suspension.rs) retains its recovery semantics: no terminal turn event, flush then close before acknowledging handoff. A common persistence settlement gate prevents a supervisor from repeating an already completed normal close; it does not erase suspension's stronger flush/error requirements.
- Retain the original initialization error. Append safe cleanup diagnostics if cleanup also fails; do not replace a replay contract error with a generic cancellation or report successful cleanup after a forced timeout. Preserve native warning policies where subordinate APIs expose only warnings, and state that limitation in the outcome.

## Native resources that the current teardown does not fully own

Calling today's cleanup function alone does not establish the retained-Arc guarantee. These small surrounding seams belong in the prerequisite's implementation/tests, with their exact scope stated:

| Resource | Current source fact | Required ownership adjustment |
| --- | --- | --- |
| Code-mode and auth prewarm | [`schedule_startup_prewarm`](../codex-rs/core/src/session/startup_prewarm.rs) spawns both without retaining their task handles. The code-mode task captures a strong Session Arc; only websocket prewarm is stored in SessionState. | Register these session-owned tasks before exposing them. A shared admission gate fences task registration with shutdown; a bare TaskTracker `close()` is not an admission fence. Cancel according to the service contract and join their wrappers. CodeModeService already cancels and joins in-flight initialization; preserve that ordering rather than dropping accepted initialization arbitrarily. Auth prewarm must not continue publishing after cleanup. |
| Inherited configuration followers | [`follow_inherited_environment_configurations`](../codex-rs/core/src/session/environment.rs) detaches tasks. They wait on `AgentStatus::Shutdown`, then may upgrade a weak Session and mutate environments. Direct failure and EOF runtime cleanup do not deliver `ShutdownComplete`. | Use explicit runtime shutdown cancellation, track/join these followers, and recheck shutdown before a configuration commit. Do not manufacture a public success event merely to stop a watcher. |
| Connection-event forwarding | [`ThreadEnvironments::start_connection_event_forwarding`](../codex-rs/core/src/environment_selection.rs) stores abort-on-drop task handles in selected environments. Retaining Session/snapshots can retain these handles after runtime teardown. | Add explicit stop/admission state for this Session's listeners and join their worker completion independent of retained service snapshots. Do not shut down the shared EnvironmentManager or another session's connection. |
| Managed proxy | [`StartedNetworkProxy`](../codex-rs/core/src/config/network_proxy_spec.rs) owns a private `_handle`; `services.network_proxy` retains it in an ArcSwapOption, and current runtime cleanup never takes/closes it. [`NetworkProxyHandle::shutdown`](../codex-rs/network-proxy/src/proxy.rs) already exists. | Make the session-owned runtime handle takeable behind an idempotent close gate; stop proxy refresh admission, fence against `managed_network_proxy_refresh_lock`, and join shutdown after execution consumers stop. A retained StartedNetworkProxy/service Arc must not preserve accepting listeners or allow a refresh to reinstall them. Shared routing dependencies remain untouched. |
| Early constructor work | Thread-start contributors run before `Arc<Session>` exists; hooks and proxy have already been constructed. Recommended-plugin prefetch is also detached before construction and uses a shared manager. | Do not move contributor calls after ModelClient construction blindly: contributors can populate thread data such as CodexResponsesHeaders that the constructor reads next. For a universal constructor-cleanup claim, add a pre-Session resource guard and track entered contributors, or separately refactor their ordering with parity tests. This lies before selected replay initialization; the post-constructed replay prerequisite must label that earlier window explicitly until addressed. Shared plugin/catalog services must not be globally shut down when one session fails. |

Process-backend `terminate_all_processes` currently requests termination and can detach backend cleanup; it does not guarantee all OS children/reapers have joined. The [execution extraction audit](EXECUTION_COMPONENT_PLAN.md) records that separate prerequisite. This Session change must accurately claim orchestration of native shutdown APIs, not complete process-tree reaping. Likewise, extension-owned arbitrary background work is only covered to the extent its lifecycle stop contract joins it.

The old activation note's persistent force/reap blocker predates the later [persistent reaping evidence](../verification/2026-09-30/component-host-persistent-reap.json). Revalidate that evidence against the activated transport revision; it does not verify the unlinked replay adapter or the Session changes proposed here.

## Concrete patch and verification sequence

After the production source gate releases, agree this common ownership shape before parallel edits. First implement native lifecycle ownership with replay absent; next attach the staged ReplayOwner and make reconstruction errors propagate. Update direct test constructors explicitly. Never activate only the new `?` at reconstruction while ordinary cleanup is still persistence-only.

Primary files: new private `session/runtime_lifecycle.rs` and dedicated tests; `session/startup.rs`, `session/session.rs`, `session/mod.rs` (constructor return/handoff/termination); `session/handlers.rs` and `session/turn_suspension.rs` (idempotent entry and settlement); `thread_manager/managed.rs` (join/weak lookup). Native task/proxy fixes belong in the small modules named in the table. No new workspace crate or public protocol is needed for this prerequisite.

Required deterministic gates, followed by the applicable native regressions:

1. Fail selected reconstruction after observing SessionConfigured with MCP, websocket/code-mode/auth prewarm and proxy work started. Retain Session and replay service Arcs. Assert each owned service closes, listeners stop, replay child is absent under its transport guarantee, and uncommitted persistence is discarded only after producers stop. Assert no native replay fallback and no ShutdownComplete/turn-count success metric.
2. Cancel at acquisition, required MCP install, replay connect, reconstruction, the post-constructor warning await and the ready-but-unconsumed startup result. Release controlled barriers after cleanup begins; late acquisition/results must be disposed, not revive services or commit history. A subsequent resume must acquire the same writer successfully.
3. Start shutdown twice, cancel the first waiter while a teardown stage is held, and verify the second stays pending until that stage and replay cleanup finish. Count SessionEnd/thread-stop hooks and underlying persistence settlement once. Inject a callback panic and verify later resource cleanup still runs and the retained report records failure without rerunning that callback.
4. Abort/panic the submission loop with no termination waiter, retaining only service/Session Arcs. Confirm the independently running supervisor performs cleanup. Later termination waiters must see completed cleanup, not merely the loop's JoinError. After dropping deliberate external references, a Weak<Session> must not upgrade; completion handles alone must not retain it.
5. Verify normal shutdown, submission EOF, suspension/recovery, managed cancellation after handoff and duplicate-start failures preserve exact history and event ordering. Keep active turn abort before thread-stop, no persistence append after shutdown, and no effect on the parent or shared managers.
6. Race replay companion-state publication and estimated-prefill completion against close. Compare the full native reconstruction under default selection and prove all selected companion state commits atomically only for the current ticket. Isolation continues to suppress global replay selection.

Existing anchors: [`startup_cancellation`](../codex-rs/core/tests/suite/startup_cancellation.rs), [`managed_threads_tests`](../codex-rs/core/tests/suite/managed_threads_tests.rs), [`rmcp_client`](../codex-rs/core/tests/suite/rmcp_client.rs) startup/shutdown cases, and [`session/tests.rs`](../codex-rs/core/src/session/tests.rs) tests `shutdown_complete_does_not_append_to_thread_store_after_shutdown`, `submission_loop_channel_close_runs_full_thread_teardown`, `submission_loop_channel_close_aborts_active_turn_before_thread_stop_lifecycle`, and the multiple/cancelled shutdown waiter cases. These existing passes do not substitute for the new failure-window tests. Runtime-only phase: browser testing is inapplicable.
