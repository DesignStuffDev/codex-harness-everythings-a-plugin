# Installed storage: slow accepted append during real Launch shutdown

Status: proposal02 addresses the two independent static-review blockers. Python
AST parsing and a bounded synthetic wire smoke passed. No real host, native
storage, installation, GUI, or >45-second runtime was exercised. The primary
checkout and original proposal bytes are untouched. See SMOKE_EVIDENCE.md.

## What this closes, and what it does not

The selected, independently installed **fixture provider** accepts one complete
`thread_store/call` / `append_items` request containing a unique GUI prompt. The
fixture retains the original physical frames **before sending them to the native
worker**. After observing the real component manager's fresh first-interrupt
acknowledgment, those frames remain held for 46 real seconds. The acknowledgment
is emitted immediately after its graceful request; observing it later makes the
test conservative. Signal-send time is recorded but is not the hold's origin.
Release then forwards the exact bytes, requires the
native append acknowledgement, native `shutdown_complete`, native exit zero,
manager exit zero, absence of every tracked descendant including zombies, and
cold recovery through the original native storage selection.

This is a real host and installation boundary test of accepted work surviving
normal Launch shutdown. It is explicitly **accepted at the installed fixture,
not admitted inside native StorageService before release**. No response delay is
used: the operation has not been forwarded at all during the hold. Native append
acknowledgement alone is not called durability; native cleanup and a cold GUI
read provide the final durability evidence for the observed fixture input.

The native storage binary is copied unchanged from the independently built,
source-removed package. The relay is an acceptance-only Python component, not a
replacement storage implementation or a newly extracted subsystem. A distinct
native-internal admission test still requires a separately built backend wrapper
or a suitable filesystem-level gate. `native::open` is private; there is no tiny
public run-stdio interceptor that could insert such a gate without a new build.

## Bounded ownership and failure

* Limits: physical frames 4 MiB; logical fixture payload 4 MiB; retained wire batch
  16 MiB; aggregate decoded partial payload 16 MiB; 64 concurrent assemblies.
  These are fixture limitations, not changes to the native component contract.
  JSON object/decoder overhead is additional; no exact process-RSS bound claimed.
* Once the target request is complete, host input stops at that gate. Later
  frames remain behind ordinary bounded pipe backpressure. No unbounded queue,
  no retry, no manufactured native acknowledgement, no reordered wire frames.
  Control traffic may also be delayed by this intentional fixture stall.
* Gate deadline is 95 seconds from fixture admission; whole relay timeout 300
  seconds. The normal test releases 46 seconds after manager SIGINT, comfortably
  inside 120-second component, 200/205-second host, 207/209-second gateway and
  210-second manager budgets. The driver's wait is observational, not a changed
  production deadline.
* Relay retains the exact child and both reader tasks. The native worker inherits
  the relay's process group. Linux parent-death SIGKILL is configured before
  exec, with a parent-identity race check, so an abruptly killed relay cannot
  knowingly leave its native child alive. This Linux-only fixture starts its
  single child before any Python worker threads.
* Every directional task is settled and its non-cancellation outcome inspected
  **after** the direct-child wait. Finished cannot be emitted until this is done.
  Only cancellation deliberately requested after terminal native EOF is accepted
  on a successful path. An earlier operation failure stays primary if cleanup
  also fails. The exact native child is waited on. Ordinary stdout backpressure is
  synchronous in this small fixture; outer production force termination remains
  the fallback if its consumer stalls. No unconditional wall-time guarantee.
* Existing sampled descendant tracking includes zombies and has its existing
  short-lived-child observation limitation. Run under the **unchanged external
  subreaper, default five-second drain**. The script checks its known SHA-256;
  it does not relax the runner. Any test emergency cleanup invalidates PASS.

## Normal acceptance sequence

1. Root finishes and freezes a real Codex CLI build; verify binary/source receipt.
2. Run ordinary reused storage, migration and default GUI gates separately.
3. Generate another fresh manual-migration fixture using the same frozen host
   and independently built original storage package. Preserve its report.
4. Run this driver beneath unchanged strict subreaper with mode `normal`.
5. Driver installs/selects relay via manager CLI; verifies unchanged copied
   native executable and pre-existing packages; launches actual desktop plugin.
6. Existing browser driver opens the real migrated conversation and sends a
   unique prompt. Wait for atomically written `accepted.json` matching thread ID
   and require no `forwarded.json` before manager SIGINT.
7. Signal **manager only**, require its fresh `Stopping presentation; allowing up
   to` acknowledgment within 15 seconds, record monotonic observation, require
   manager still alive and operation still unforwarded for >45 real seconds
   **after that observation**, then create release.
8. Require exact native append result, shutdown receipt and child/manager zero
   exit; require all tracked processes gone, including zombies. Browser closes.
9. Select original native package, remove relay activation and launch cold GUI.
   Require held prompt in recovered history and complete a new deterministic
   streamed turn. Save screenshot. Normal manager shutdown must pass again.
10. Verify immutable host/native package/input evidence, and outer strict runner
    exit zero with no lingering descendants. Preserve actual tested source and
    all receipts, including any original failed attempt separately.

## Forced acceptance sequence

Use a different fresh fixture and mode `forced`. After accepted receipt, signal
manager once, observe its acknowledgment, wait two seconds while still held,
then signal manager a second
time. Require nonzero manager exit and the literal durability uncertainty
message, operation never forwarded, no tracked descendants, and no test-induced
emergency cleanup. Cold launch original native selection; require held prompt
absent, previous history available, and a new ordinary turn completes.

The observed absence of this deliberately unforwarded write does **not** turn the
forced operation into a durability success. Its report stays
`forced_shutdown_explicitly_unknown`; other accepted operation outcomes remain
uncertain. PASS means only the forced-error/cleanup/recovery scenario passed.
